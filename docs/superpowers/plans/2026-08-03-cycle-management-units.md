The rank/staff-role guard convention is `associate.getRole() == AssociateRole.ASSOCIATE` (process only associates), matching the *live* `chk_associate_rank_required` constraint (V4, not V3) — reuse this exact guard for any future unit that needs to skip non-ASSOCIATE roles, don't re-derive it (note: unit 7/Sponsor Matching and unit 9/Reward both deliberately have NO such guard — Decision #7/#8's carve-outs apply them to Admin in full — so don't copy that omission's absence-of-guard as a new default without checking each unit's own spec decision). `ledger_entry.source_ref` NOT NULL + unique constraint (V17) and `LedgerEntryRepository.existsByAssociateIdAndCycleIdAndIncomeTypeAndSourceRef(...)` remain the idempotency pattern for every other income type; unit 9's own `LedgerEntryRepository.existsByAssociateIdAndIncomeTypeAndSourceRef(...)` (deliberately no `cycleId`) is the one deviation, because a RewardTier is awarded once EVER, not once per cycle (Decision #8) — don't copy that method's shape for any future cycle-scoped income type without checking the same reasoning applies. Unit 9 made one judgement call beyond the spec's literal text, confirmed with the user: `RewardTier`s with `cashReward &lt;= 0` are skipped entirely (no ledger entry, no idempotency anchor) rather than writing a $0 entry to anchor a perk-only tier — harmless (re-evaluated cheaply each future cycle) but worth knowing if a future unit ever needs to enumerate "all tiers this associate has crossed," since a zero-cash crossed tier won't show up in `LedgerEntry` at all.
