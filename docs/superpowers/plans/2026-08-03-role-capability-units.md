**Unit 2 merged 2026-08-13 (`63ce818..232c00d`) — caught and fixed a real regression before merge.** Its implementing agent initially misclassified 3 failing `CycleClose*IntegrationTest` tests as "unrelated in-flight cycle-management work" — verified false by running the same 3 classes against a clean `master` baseline directly (`BUILD SUCCESS`, 4/4 green there, 2 failures + 1 error in the unit-2 worktree). Root cause: `CycleService.close()` calls `associateRepository.findAll()` unscoped, and the new `V18__seed_founding_admin.sql` migration's permanent `ADMIN`-role root row (no children) gets swept into every `@SpringBootTest` integration test's leg-volume rollup, shifting count-based assertions off by exactly one (`expected: 8 but was: 9`, `expected: 6L but was: 7L`) and leaving an orphaned `leg_volume` row `CycleCloseConcurrencyTest.cleanUp()` didn't account for on delete. Fix (`232c00d`, code-review-verified correct against the spec's own "Resolved decisions #2" — the engine including the root's own zero-volume leg-volume row is intended behavior, not a bug): scoped the 3 tests' assertions to their own fixture associate IDs instead of counting unscoped, and fixed `cleanUp()`'s delete order (leg_volume before cycle) to match the pattern the other two integration tests already used. **Lesson for future units that seed permanent rows into every environment: always diff integration-test results against a clean master baseline before trusting an implementer's "unrelated/pre-existing" classification — don't take it on faith even when the reasoning sounds plausible.**
