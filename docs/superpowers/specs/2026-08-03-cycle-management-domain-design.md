# Cycle Management Domain (Settlement Batch, Cycle Close, Admin Cycle Views)

## Context

The `cycle` package (`Cycle`, `CycleStatus`, `CycleRepository`, `NoOpenCycleException`) is entity+repository only — nothing anywhere creates, opens, or closes a cycle, and no controller exists for either role. `docs/superpowers/specs/2026-08-03-sales-domain-design.md` (Sales) fixes half of that gap by adding `CycleService.getOrOpenCurrent()`: finds the `OPEN` cycle whose period covers today (1st–15th / 16th–30th of the current month), creates one if none exists. Sales calls this on every sale recorded, and computes Direct Income synchronously. Everything else in `mlm-land-platform-spec.md` §3's compensation engine — leg-volume rollup, Matching, Sponsor Matching, Royalty, Reward/Rank, deductions, KYC-gating — is unbuilt. This spec is that batch, plus the admin-facing cycle-close trigger/monitor endpoints and the settlement side of the `(associate_id, cycle_id, income_type, source_ref)` idempotency guarantee §3 calls for.

This spec builds directly on Sales' `CycleService.getOrOpenCurrent()` — it is not redefined here. It also builds on `docs/superpowers/specs/2026-08-03-role-capability-data-visibility-design.md`'s resolved two-role model: Admin sits at the root of the binary tree (`parent_id = NULL`) and participates in compensation like any other node, with one schema-level exception already baked into the codebase (see Decisions #7): `associate.rank_id` is nullable only for `role = 'ADMIN'` (`chk_associate_rank_required`, `V3__account_provisioning.sql`), and `AdminBootstrapRunner` already sets it to `null`. So "Admin has no rank" isn't a hypothetical this spec has to guess at — it's an existing, enforced constraint this spec's batch has to respect.

**Surprise finding that changes the shape of this spec**: the reconciliation audit in the role-capability spec assumed royalty-by-rank and reward-threshold-bonus data didn't exist. They do. `com.plotchain.compensation` already has `RoyaltyBonusRate` (`plan_version_id`, `rank_id`, `royalty_pct`, unique per plan-version+rank, FK to `rank_tier`) and `RewardTier` (`plan_version_id`, `tier_level`, `volume_threshold`, `cash_reward`, `perk_description`, unique per plan-version+tier), both introduced by `V8__compensation_plan.sql` for the Compensation Rules Config screen (`CompensationPlanController`, admin-only, versioned) and currently read-only from the batch's perspective — nothing writes ledger entries or evaluates them yet. `Associate.cumulativeMatchedVolume` also already exists (`V1`, used today by `DashboardService` purely for read-only "progress to next rank" display) — this is the exact "cumulative matched-pair volume" field §3 step 6 evaluates against thresholds. No new columns are needed for royalty or reward data; this spec's data-model additions are narrower than the brief anticipated: idempotency constraint, a couple of new repository query methods, and (per Decision #10) tightening `ledger_entry.source_ref` to `NOT NULL`.

## Scope

**In scope**: `CycleService` gains cycle-close/settlement capability — an admin-triggered "close current cycle, run the batch, open the next cycle" action, implementing `mlm-land-platform-spec.md` §3 steps 2–8 (step 1, Direct Income, is Sales' job). `GET /api/admin/cycles` (history/list) and `GET /api/admin/cycles/{id}` (detail + per-income-type totals) for admin monitoring. `POST /api/admin/cycles/{id}/close` to trigger the batch, safely re-triggerable on a failed/in-progress close without double-crediting. The associate-facing "own cycle-scoped reports" question (resolved below: no new endpoint here).

**Out of scope** (deferred, one sentence each):
- Direct Income — Sales' job, already specified there.
- Wallet balance crediting and the `CLOSED → PAID` cycle transition — a future Wallet/Withdrawal spec decides whether wallet balance increments when this batch marks entries `PENDING`-and-KYC-clear or via a separate settlement step, and how/when `Cycle.status` ever reaches `PAID`; this spec only ever writes `OPEN → CALCULATING → CLOSED`.
- Reconciling `CARRIED_FORWARD` (KYC-withheld) ledger entries once an associate's KYC later verifies — the append-only ledger means this batch never mutates a past cycle's entries, so "does a later KYC approval retroactively unlock last cycle's withheld income" is the same future Wallet/KYC-follow-up question as the point above, not answered here.
- Any scheduled/cron automation of cycle-close — this spec is admin-triggered only, per the role matrix's "Admin: trigger/monitor/re-run" language.
- Incremental (on-sale) leg-volume updates — the NFR in `mlm-land-platform-spec.md` §6 flags this as a future scale concern; this batch recomputes leg volume from scratch each cycle close (see Decision #4), which is adequate at this platform's expected scale and is explicitly the documented starting point, not a silent shortcut.

## Decisions

1. **The batch runs synchronously inside `POST /api/admin/cycles/{id}/close`, in one `@Transactional` method, all-or-nothing.** No Kafka, no async worker exists anywhere in this codebase (the architecture diagram in `mlm-land-platform-spec.md` §4 is aspirational, not what's built — Sales already established plain synchronous Spring Boot + Postgres as the real pattern). A single transaction keeps "never double-credit on partial failure" simple and, combined with Decision #2's row lock, makes double-crediting *structurally impossible* rather than merely checked-for: either the whole batch commits (cycle reaches `CLOSED`) or none of it does (cycle is left exactly where it started, `OPEN`) — there is no partially-committed state a retry could collide with. The cost is a longer-held transaction and lock on a large tree, and an all-or-nothing retry (a late failure means redoing everything, not resuming from where it broke) — acceptable at this platform's scale (a regional real-estate MLM, not a global consumer app); revisit (likely via chunking, with Decision #12's idempotency constraint as the safety net that makes chunked partial commits safe to resume) if associate counts or batch duration grow enough for this to matter (Open Question #3).

2. **Concurrency guard: `SELECT ... FROM cycle WHERE id = :id FOR UPDATE`, acquired as the *first* statement inside that same transaction — not a separate pre-transaction commit.** A second `POST /close` against the same cycle blocks on this row lock until the first request's transaction resolves (commit or rollback), then re-reads the row's status under its own lock: `CLOSED`/`PAID` (first request succeeded) → 409 `CycleAlreadyClosedException`; still `OPEN` (first request's transaction rolled back on an exception, or was abandoned by a JVM crash that dropped the DB connection and released the lock — either way nothing committed) → proceeds normally. This single mechanism handles both the "double-click" case (second request blocks, then loses cleanly) and the "retry after failure" case (second request blocks, then finds `OPEN` and simply runs fresh) with no separate recovery path and no window where two attempts run concurrently against the same cycle — which matters beyond wasted work: `cumulativeMatchedVolume`'s read-modify-write (Decision #6) is not itself atomic, so two genuinely concurrent executions could lose an update; the lock rules that out entirely rather than relying on the ledger's idempotency check to paper over it. The trade is a blocking wait instead of an immediate fast-fail on a double-click — acceptable here because the caller's own HTTP request is already the only progress signal this design provides (no separate polling/heartbeat exists to report "still running" mid-batch), so a second click waiting for the first's answer is no worse a UX than an instant, uninformative rejection would be.

3. **"Re-run" means retrying `POST /close` on the same cycle after a previous attempt failed, and Decision #2's design makes this need no special-casing.** A failed attempt's transaction rolls back or is abandoned, leaving the cycle's committed status at `OPEN` — indistinguishable from a cycle that was never attempted. The next call simply finds it `OPEN` and runs the batch fresh; Decision #12's idempotency check is not what makes this safe (a full rollback leaves zero entries to collide with) but is kept as the literal constraint `mlm-land-platform-spec.md` §3 calls for and as forward-compatible insurance for the day the batch is chunked into multiple smaller transactions (Open Question #3), at which point a retry genuinely could encounter partially-committed prior work. Reopening an already-`CLOSED` cycle's settlement (e.g. because a sale was voided after close) is a materially different, riskier operation — it would need to reverse already-issued ledger entries, unwind rank advancement, and potentially claw back reward bonuses — and is not designed here; `POST /close` on a `CLOSED`/`PAID` cycle always 409s, full stop. Append-only-ledger NFR (`mlm-land-platform-spec.md` §6) argues against ever doing this by mutation regardless.

4. **Leg-volume rollup is a single in-memory pass per close, not N recursive SQL queries.** Load every `Associate` (id, parentId, position, sponsorId, rankId, cumulativeMatchedVolume) and every `RECORDED` `Sale` for the closing cycle (grouped by associateId) into memory once, build the parent→children adjacency in Java, then walk leaf-to-root: `subtreeVolume(node) = sum(node's own RECORDED sales this cycle) + subtreeVolume(leftChild) + subtreeVolume(rightChild)` (0 for a missing child), computed via post-order DFS from the single root (the Admin row — per the role-model spec there is exactly one root post-migration). For each node with at least one child: `newLegVolume.leftLegVolume = subtreeVolume(leftChild) + priorCycleLegVolume.carriedForwardLeft`, same for right, where `priorCycleLegVolume` comes from `LegVolumeRepository.findByAssociateIdAndCycleId(node, previousClosedCycleId)` (0/empty if none — first-ever cycle). `previousClosedCycleId` = `cycleRepository.findFirstByStatusOrderByPeriodStartDesc(CycleStatus.CLOSED)` (this existing method, already used for `OPEN`, works unmodified for `CLOSED`). One `LegVolume` row is written per associate per cycle, unconditionally (even all-zero), for a consistent one-row-per-pair audit trail — matches `DashboardService`'s existing "row may not exist, treat as `LegVolume.empty()`" tolerance for cycles before this batch ever ran, without relying on it going forward.

5. **Matching Income is one `LedgerEntry` per associate per cycle**, `grossAmount = min(leftLegVolume, rightLegVolume) × matchingIncomePct / 100`, written for every associate with a nonzero matched amount (zero-matched associates get no entry — an entry with `grossAmount = 0` carries no information and would just be noise in every associate's income statement). `sourceRef = legVolume.id` (the just-written `LegVolume` row for that associate+cycle) — deterministic, non-null, and naturally unique per associate per cycle, satisfying the idempotency constraint without inventing a synthetic key. The excess on the larger leg (`abs(left − right)`) is written into that *same* `LegVolume` row's `carriedForwardLeft`/`carriedForwardRight` (whichever leg was larger) for the next cycle's rollup to consume per Decision #4 — not into a new/separate row.

6. **`associate.cumulativeMatchedVolume` accrues the raw matched *volume* (`min(left, right)`), not the matching *income* (post-percentage) amount**, matching the field's existing use in `DashboardService` (compared directly against `RankTier.volumeThreshold`, itself a volume, not a currency-scaled income figure) and matching `mlm-land-platform-spec.md` step 6's "cumulative matched-pair volume" wording precisely. This increment happens as part of the Matching step, before rank progression or reward evaluation reads it.

7. **Rank progression is a new sub-step inserted between Sponsor Matching and Royalty, not a separate numbered step in `mlm-land-platform-spec.md`'s list — because Royalty (step 5) can't run without it.** Step 5 says royalty% is "looked up from a rank-based table... varies by achieved level" — nothing in the existing codebase ever advances `associate.rankId` (it's set once, to the lowest tier, at provisioning, and never touched again; confirmed by grepping every `setRankId` call). This batch is therefore the thing that advances it: after each associate's `cumulativeMatchedVolume` is updated (Decision #6), compare it against `RankTierRepository.findAllByOrderByRankOrder()` and set `associate.rankId` to the highest tier whose `volumeThreshold` is now met (never *demote* on a bad cycle — rank is a high-water mark, matching how `RewardTier`/reward crossing is also framed as one-directional in step 6's "don't re-award" language). **Skipped entirely for Admin** (`rankId == null` by the `chk_associate_rank_required` constraint) — not a special case in the rollup/matching math (Admin's leg volumes and matched income compute identically to any node, per the role-model spec's resolved decision #2), just a guard on this one sub-step because there is structurally no rank to advance into.
   Royalty (step 5) then looks up `RoyaltyBonusRateRepository` for the associate's *current* (i.e., just-possibly-advanced-this-cycle) `rankId` — an achievement crossed this cycle earns this cycle's royalty rate immediately, which is the more generous and more defensible reading of "achieved level" than requiring a full cycle's lag. **Also skipped for Admin** (no `rankId` to look up a rate for) — this is the one place this spec *does* deviate from the role-model spec's literal "no special-cased exclusion" language, because `RoyaltyBonusRate` is structurally rank-keyed and Admin structurally has no rank (a constraint that spec's own migration approach section left untouched). Matching and Sponsor Matching, which have no rank dependency, are unaffected and do apply to Admin in full.

8. **Reward/Rank Income (step 6) uses `RewardTier`, evaluated against the same updated `cumulativeMatchedVolume`, independently of rank** — `RewardTier` has no FK to `rank_tier`, only to `compensation_plan_version`, so unlike Royalty this one *does* apply to Admin (consistent with the role-model spec's decision #2, and not blocked by any schema constraint). For each `RewardTier` (ordered by `tierLevel`) whose `volumeThreshold <= associate.cumulativeMatchedVolume`: check `LedgerEntryRepository` for an existing entry with `(associateId, incomeType=REWARD, sourceRef=tier.id)` — **no `cycleId` filter**, because a tier is awarded once ever, in whichever cycle first crosses it, and later cycles must not re-award it even though `cumulativeMatchedVolume` stays above the threshold forever after. If none exists, write one: `grossAmount = tier.cashReward`, `sourceRef = tier.id`. `perkDescription` (e.g. "smartwatch") is not itself money and gets no separate ledger line or `PERK`-type entry — it's descriptive metadata already reachable by looking up the `RewardTier` row via this entry's `sourceRef`, exactly how an income-statement UI would render "Reward: ₹5,000 + smartwatch" from one entry. `IncomeType.PERK` stays unused by this batch; nothing in `mlm-land-platform-spec.md` §3 calls for a monetary line item distinct from `REWARD`, and perks have no amount to put in `gross_amount` in the first place.

9. **Sponsor Matching (step 4) is one `LedgerEntry` per (sponsor, direct sponsee, cycle)** — itemized per sponsee, not aggregated into one lump sum, because §3's phrasing ("11% × matching income of *each* direct sponsee") and `LedgerEntry.sourceRef`'s per-row nature both point to one line per sponsee, giving full audit traceability ("this bonus derives from this sponsee's matching entry"). Runs as a genuine second pass after every associate's Matching entry (Decision #5) is written: for each associate with `sponsorId IS NOT NULL`, find their sponsor, and for each of the sponsor's direct sponsees (`AssociateRepository.findBySponsorId(sponsorId)` — new method, mirrors the existing `findByParentId`), look up that sponsee's Matching entry for this cycle via `LedgerEntryRepository` (new method: find-by-associate-cycle-type, or reuse the existing sum query's shape) and compute `grossAmount = sourceMatchingEntry.grossAmount × sponsorMatchingPct / 100`; `sourceRef = sourceMatchingEntry.id`. Every derived-income step (Sponsor Matching here, and implicitly Royalty) bases its percentage on the *source* entry's `grossAmount`, never `netAmount` — deductions are applied once, per-entry, at the point each entry is created (Decision #10), and basing a derived calc on an already-net figure would double-apply that effect implicitly.

10. **Deductions (step 7) apply inline, at the point each entry is created, using the same math Sales already established**: `tdsDeduction = grossAmount × tdsPct/100`, `adminDeduction = grossAmount × adminChargeWithoutPanPct/100` (always the without-PAN tier — `Associate` has no `pan_number` field, same documented simplification Sales already made and flagged in its own Open Questions), `netAmount = grossAmount − tdsDeduction − adminDeduction`. Percentages come from the `CompensationPlanVersion` resolved once per batch run via `findFirstByEffectiveFromLessThanEqualOrderByEffectiveFromDesc(cycle.getPeriodStart())` — **deliberately the cycle's `periodStart`, not `LocalDate.now()`** (the pattern Sales and `DashboardService` both use for point-in-time reads). This is a considered deviation, not an oversight: Direct Income is computed the instant a sale happens, so "now" and "during the cycle" are the same instant and either lookup is equivalent. This batch computes cycle-*aggregate* income after the fact, potentially days after the cycle closed conceptually, so "now" (close time) could pick up a plan version an admin published *after* the cycle's volume already accrued — silently changing the rate volume was earned under. Resolving against `periodStart` instead is what actually satisfies the "rule versioning... historical cycles aren't affected by later changes" NFR (`mlm-land-platform-spec.md` §6) for this batch's math, and doesn't touch `getOrOpenCurrent()` or any other Sales-owned behavior. The existing-but-unused `cycle.compensation_plan_version_id` FK column is not repurposed here — leave it for whichever future work actually wants to stamp-and-freeze the version at cycle-open time; this spec's periodStart lookup gets the same correctness without needing it.

11. **KYC-gating (step 8) manifests as a status choice at entry-creation time, not a post-hoc flip.** The real `LedgerEntryStatus` enum (`PENDING, CARRIED_FORWARD, PAID, REVERSED`) has no `PAYABLE` value, so "entries stay pending... only become payable once verified" is re-read against what's actually available: every entry this batch creates checks `associate.kycStatus` at creation time — `VERIFIED` → `status = PENDING` (same meaning Sales already gives `PENDING`: computed, not yet paid, eligible for whatever the future Wallet/payout step does); anything else (`PENDING` or `REJECTED` KYC) → `status = CARRIED_FORWARD`, repurposing that existing-but-previously-unused enum value to mean "computed and correctly calculated, but withheld because the beneficiary isn't KYC-verified" — a real distinct state, not a synonym for pending-payment. This is a genuine, minimal reuse of schema that already exists rather than adding a fifth status value. What (if anything) transitions a withheld `CARRIED_FORWARD` entry once KYC later verifies is out of scope (see Out of Scope).

12. **Idempotency constraint is `UNIQUE (associate_id, cycle_id, income_type, source_ref)` on `ledger_entry`, and `source_ref` becomes `NOT NULL`.** Postgres does not treat `NULL = NULL` as a match inside a unique constraint, so a nullable `source_ref` would silently defeat this exact guarantee for any income type that ever left it null — and by the time this spec's batch exists, every income type populates it meaningfully (Direct: `sale.id`; Matching: `legVolume.id`; Sponsor Matching: the sponsee's Matching `LedgerEntry.id`; Royalty: `legVolume.id`, same as Matching, since both derive from the same cycle-computed matched-pair volume for that associate; Reward: `rewardTier.id`) — see Data model for the migration that tightens this, applied after Sales' migration that first adds the column as nullable. The batch writes every entry via *check-then-insert* — `existsBy(associateId, cycleId, incomeType, sourceRef)` before each write, skip if true — rather than insert-and-catch-a-constraint-violation. Given Decision #1/#2's all-or-nothing, single-locked-transaction design, this check is not what prevents double-crediting *today* (a rolled-back retry has nothing to collide with; a `CLOSED` cycle can't be re-entered at all) — Reward's cross-*cycle* check (Decision #8, deliberately un-scoped by `cycleId`) is the one idempotency check doing real work right now. The per-write check for the other four income types is kept anyway for two reasons: it's the literal constraint `mlm-land-platform-spec.md` §3 asks for, and it's the mechanism that makes a *future* chunked/multi-transaction version of this batch (the natural answer to Open Question #3, if this platform's tree ever outgrows one big transaction) safe to resume without a redesign — the DB constraint is the hard backstop underneath it either way.

13. **No new associate-facing endpoint.** `GET /api/associates/me/dashboard` (existing, `DashboardService`) already gives an associate their current cycle's direct/matching totals, leg volumes, projected match, and rank progress — a "cycle-scoped report," per the role matrix's "Associate sees own cycle-scoped reports only, no control." The itemized per-income-type breakdown (Sponsor/Royalty/Reward line items, historical cycles) is squarely what the sibling Income/Ledger spec's `GET /api/associates/me/ledger` is for — this spec depends on that endpoint existing to fully satisfy the matrix row, but does not design it here (per the task brief, that spec is being written in parallel and its exact shape isn't assumed). This spec's only endpoints are the three admin ones below.

## Data model

**Migration** (new, lands after Sales' migration that adds `ledger_entry.source_ref` as nullable):

```sql
ALTER TABLE ledger_entry ALTER COLUMN source_ref SET NOT NULL;
ALTER TABLE ledger_entry ADD CONSTRAINT uq_ledger_entry_idempotency
    UNIQUE (associate_id, cycle_id, income_type, source_ref);
```

No other schema changes. `RoyaltyBonusRate`, `RewardTier`, `Associate.cumulativeMatchedVolume`, `Associate.rankId` (nullable for `ADMIN` only), `LegVolume`, `Cycle`/`CycleStatus` all already exist and are reused as-is.

**New repository methods:**
- `AssociateRepository.findBySponsorId(UUID sponsorId): List<Associate>` — Sponsor Matching's per-sponsor sponsee lookup (Decision #9).
- `LedgerEntryRepository.findByAssociateIdAndCycleIdAndIncomeType(UUID, UUID, IncomeType): Optional<LedgerEntry>` — locates a sponsee's Matching entry for Sponsor Matching's `sourceRef`/base amount (Decision #9).
- `LedgerEntryRepository.existsByAssociateIdAndCycleIdAndIncomeTypeAndSourceRef(UUID, UUID, IncomeType, UUID): boolean` — the idempotency check (Decision #12), used before every write this batch makes.
- `LedgerEntryRepository.existsByAssociateIdAndIncomeTypeAndSourceRef(UUID, IncomeType, UUID): boolean` — the reward-already-awarded check (Decision #8); deliberately omits `cycleId`.
- `LedgerEntryRepository.sumNetAmountByCycleAndType` / `sumNetAmountByCycle` (existing) — reused as-is for the admin cycle-detail view's per-income-type totals; no new query needed there.
- `RoyaltyBonusRateRepository.findByPlanVersionIdAndRankId(UUID, UUID): Optional<RoyaltyBonusRate>` — new, narrower than the existing `findAllByPlanVersionId`, for the single-rank lookup Royalty needs per associate.
- A new `SaleRepository` method (owned by the Sales package, added here since Sales didn't need it): `findByCycleIdAndStatus(UUID cycleId, SaleStatus status): List<Sale>` — the batch's one query to load this cycle's `RECORDED` sale volume for the in-memory rollup (Decision #4).

**New Java types**: `CycleAlreadyClosedException`, `SettlementService` (new class in the `cycle` package, alongside `CycleService` — the batch orchestrator; kept separate from `CycleService` because `CycleService` is Sales' minimal `getOrOpenCurrent()` and this is a much larger, differently-scoped piece of logic, not because they can't both live in the same package), `SettlementResult` (record — counts of entries written per income type, total net amount, for the close endpoint's response), `CycleController`, `CycleSummaryResponse`/`CycleDetailResponse` (admin cycle list/detail DTOs).

## Flows

### Settlement batch — invoked by `POST /api/admin/cycles/{id}/close`

Runs once, synchronously, inside one transaction (Decision #1):

1. **Lock and resolve inputs.** `SELECT ... FOR UPDATE` the `Cycle` row (Decision #2). If status is not `OPEN`, stop here (see endpoint flow below for the resulting response). Otherwise flip `status = CALCULATING` (write only — see Decision #2's note on why this isn't externally observable mid-batch under this design). Resolve the `CompensationPlanVersion` effective as of `cycle.getPeriodStart()` (Decision #10). Load every `Associate` and every `RECORDED` `Sale` for this cycle into memory (Decision #4).
2. **Leg-volume rollup.** Post-order DFS from the root (Admin). For each associate: compute `subtreeVolume`, then `leftLegVolume`/`rightLegVolume` = child subtree volume + prior cycle's carried-forward for that leg. Write one `LegVolume` row per associate (Decision #4).
3. **Matching Income.** For each associate with `min(left, right) > 0`: write a `MATCHING` `LedgerEntry` (idempotency-checked first, Decision #12) with `grossAmount = min(left,right) × matchingIncomePct/100`, deductions applied (Decision #10), KYC-gated status (Decision #11), `sourceRef = legVolume.id`. Update that `LegVolume` row's `carriedForwardLeft`/`carriedForwardRight` with the unmatched excess (Decision #5). Increment `associate.cumulativeMatchedVolume += min(left,right)` (Decision #6).
4. **Rank progression.** For each non-Admin associate: advance `rankId` to the highest `RankTier` now qualified for by the updated `cumulativeMatchedVolume` (Decision #7). Never demotes.
5. **Sponsor Matching.** Second pass, requires step 3 complete tree-wide. For each associate with a direct sponsee who has a Matching entry this cycle: write a `SPONSOR_MATCHING` entry per sponsee (Decision #9), `sourceRef` = that sponsee's Matching entry id.
6. **Royalty.** For each non-Admin associate with a Matching entry this cycle: look up `RoyaltyBonusRate` for `(planVersion, associate.rankId)` (post-step-4 rank); if found, write a `ROYALTY` entry, `grossAmount = matchedPairVolume × royaltyPct/100`, `sourceRef = legVolume.id` (same as Matching). Skipped if no rate configured for that rank (not an error — some low ranks may have no royalty tier).
7. **Reward/Rank Income.** For every associate (including Admin): walk `RewardTier`s in `tierLevel` order, award (idempotency-checked by tier, not cycle — Decision #8) any newly-crossed tier.
8. **Close and reopen.** `cycle.status = CLOSED`. Call `cycleService.getOrOpenCurrent()` — since "today" no longer falls in the now-closed cycle's period once its period has genuinely ended, this creates the next period's cycle (same method Sales already depends on, untouched). Return `SettlementResult`.

If any step throws, the whole transaction rolls back — including the `CALCULATING` flip from step 1, since it was never a separate commit (Decision #2) — leaving the cycle exactly as it was before the call, `OPEN`. A JVM crash mid-batch has the same effect: the DB drops the abandoned connection, the transaction is never committed, and the row lock releases. Either way, the next `POST /close` call (Decision #3) finds the cycle `OPEN` and simply runs again from scratch.

### `GET /api/admin/cycles` — ADMIN-only

Paginated (`page`/`size`, clamped 0–100, matching every other admin list endpoint), optional `status` filter. Each row: `id`, `periodStart`, `periodEnd`, `status`.

### `GET /api/admin/cycles/{id}` — ADMIN-only

Same fields plus a per-income-type breakdown: `{ incomeType, totalNet }` for each of `DIRECT/MATCHING/SPONSOR_MATCHING/ROYALTY/REWARD` (via the existing `sumNetAmountByCycleAndType`, no new query) and the cycle's overall `totalNet` (`sumNetAmountByCycle`, existing). This is the "monitor" half of "trigger/monitor/re-run."

### `POST /api/admin/cycles/{id}/close` — ADMIN-only

1. Look up `Cycle` by id (plain read, pre-lock) → 404 if missing.
2. Acquire the row lock and re-check status (Decision #2) — this may block if another request against the same `{id}` is already inside the transaction. Status `CLOSED`/`PAID` → `CycleAlreadyClosedException` → 409. Status `OPEN` → proceed (this covers both a first attempt and a retry after a prior failed attempt, per Decision #3 — both look identical at this point).
3. Run the settlement batch (above), inside the same locked transaction.
4. Return `SettlementResult` (200): entries written per income type, total net amount, the new current cycle's id.

## Error handling

| Exception | HTTP | Trigger |
|---|---|---|
| `CycleNotFoundException` (new, or reuse pattern from other `*NotFoundException`s) | 404 | `{id}` doesn't resolve to a `Cycle` |
| `CycleAlreadyClosedException` (new) | 409 | closing a cycle whose status is already `CLOSED` or `PAID` (checked under the row lock, Decision #2 — including the case where a concurrent request that was blocking on the lock wakes up to find the cycle it was waiting on just got closed by the request it was blocked behind) |
| `NoOpenCycleException` (existing) | — | not expected to surface here; `getOrOpenCurrent()` at step 8 always creates one if missing, this is the one caller that can never observe "no open cycle" as an error |

## Testing

- `SettlementServiceTest`: leg-volume rollup matches hand-computed expected values on a small fixture tree (3–4 levels, mixed L/R, some leaf sales, some carried-forward from a seeded prior `CLOSED` cycle's `LegVolume` rows); Matching entry gross/net math against a stubbed `CompensationPlanVersion`; excess correctly written to `carriedForwardLeft`/`Right` on the larger leg; Sponsor Matching produces one entry per direct sponsee, based on that sponsee's Matching `grossAmount`; rank advances exactly to the highest newly-qualified tier and never regresses; Royalty entry uses the *post-advancement* rank's rate; Reward tier awarded exactly once across multiple cycles even as `cumulativeMatchedVolume` stays above threshold (re-running the batch, or running a later cycle, doesn't re-award); Admin participates in rollup/matching/sponsor-matching/reward but gets no rank advancement and no royalty entry; KYC-unverified associate's entries land as `CARRIED_FORWARD` not `PENDING`.
- **Idempotency test**: force a mid-batch failure (e.g. a stubbed exception after step 5) against a cycle with real sales data; assert the transaction rolled back completely — zero `LedgerEntry` rows, `associate.cumulativeMatchedVolume`/`rankId` unchanged, `Cycle.status` back to `OPEN`; then call `POST /close` again against the same cycle without the stub and assert it succeeds normally with the full, correct set of entries (not double-written, since the failed attempt left nothing behind to collide with). Separately, assert the reward-tier check in Decision #8 does span cycles: run the batch across two consecutive cycles for an associate whose volume already crossed a tier in the first, and confirm no second `REWARD` entry for that tier appears in the second cycle's output.
- **Concurrency test**: two simultaneous `POST /close` calls against the same `OPEN` cycle (e.g. one held open mid-transaction via a test hook, or asserted via row-lock wait behavior) — the second blocks until the first resolves, then gets 409 `CycleAlreadyClosedException` once the first succeeds; the batch's side effects (ledger entries, rank advancement) happen exactly once, never twice.
- `CycleControllerTest` (MockMvc + real JWT, mirroring `SaleControllerTest`'s shape): 200 on list/detail, 200 + `SettlementResult` on close, 409 on closing an already-`CLOSED` cycle, 404 on a nonexistent id.
- `SecurityConfigTest` additions: all three `/api/admin/cycles*` routes are ADMIN-only (associate token → 403).
- `AssociateRepositoryTest`: `findBySponsorId` returns only direct sponsees, not the whole downline.

## Resolved decisions (post-review)

1. **Royalty stays skipped for Admin.** Confirmed: schema-driven skip (Decision #7) is the permanent posture, not a placeholder. If Admin ever needs a real rank, that's a future spec's problem to solve from scratch, not a case this batch guards for.
2. **"Re-run" never means reopening a `CLOSED` cycle. Corrections always post forward, into a later cycle, never by mutating a closed one.** A `CLOSED`/`PAID` cycle's `POST /close` stays a hard 409 with no exception, permanently — not just "not designed yet." If a sale is voided after its cycle closed, the correction (a reversal or an adjustment) is scoped to whichever cycle is open *when the correction is made*, not retroactively applied to the cycle the original sale belonged to. This is now a firm decision, not an open question: it's the only posture consistent with the append-only-ledger NFR, and reopening a closed cycle (unwinding rank advancement, clawing back rewards already paid into associates' wallets by the Wallet spec's crediting step) has no clean design and isn't worth inventing one for.

## Open questions

1. **Batch performance at real scale isn't validated here.** Decision #4's single in-memory pass is better than N recursive queries, but "load every associate and every sale for the cycle into memory inside one transaction" still has a ceiling. `mlm-land-platform-spec.md` §6 already flags incremental rollup as future work; this spec doesn't attempt to size that ceiling against this company's actual expected associate count, so there's no data-backed answer to "does this need chunking/pagination before launch, or is one Patna-region company's tree small enough that it never matters." Deferred, not guessed at — no action needed until real usage data exists.
2. **KYC-carry-forward reconciliation is resolved, but lives in the Wallet/Withdrawal spec, not here.** See `docs/superpowers/specs/2026-08-04-wallet-withdrawal-domain-design.md`'s new "KYC-verification-triggered reconciliation sweep" decision — when an associate's KYC later verifies, their `CARRIED_FORWARD` entries (from any past cycle, including already-`PAID` ones) get credited directly, without reopening or re-touching the cycle they originated in. That design respects decision #2 above: the cycle itself is never revisited, only the individually-withheld entry is.
