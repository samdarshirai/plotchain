# Settings & Admin Screens: Design Parity Spec

## Context

A two-pass design audit (source-level diff across all 16 screens behind the admin header nav, then a live browser pass against a seeded dev database) found the color-token migration to Viraj Acres branding is already complete and structurally correct (`frontend/src/styles/_tokens.scss` matches root `DESIGN.md` exactly, the header/nav restructure to category+item pills already landed). The gaps are narrower than a first read suggests: a handful of shared-primitive bugs that ripple across many screens, a few screens with real typeface/color slips, and — the thing this spec exists to sort out — **several findings that looked like bugs against the plain mockup but turn out to be correct once the right, more specific documentation is consulted.** That reconciliation is this spec's main job; §"Documentation hierarchy" below is the part worth reading even if nothing else is.

Two prior working documents (published as Artifacts, not in this repo) did the raw comparison work this spec draws from; their findings are restated here directly rather than linked, since Artifacts aren't reachable from the codebase. This spec is the durable, doc-cited version of that work.

## Documentation hierarchy (read this first — it changes several verdicts below)

Four sources govern these screens, and they don't all agree with each other:

1. **`DESIGN.md`** (repo root) — the Viraj Acres brand system. Created 2026-08-16, twice refined since (last: 2026-08-21). Canonical for color, typography, the Seal Card, motion, icons, and the app-wide Do/Don't rules (§9).
2. **`docs/design/viraj_acres_settings_mockup/Viraj_Acres_Settings.dc.html`** — the literal pixel-level mockup for every screen behind the header nav *except* the four named in (3). Authoritative for layout/sizing/spacing on the screens it covers, since `DESIGN.md` doesn't specify per-screen pixel detail. (`docs/design/viraj_acres_settings_mockup/DESIGN.md` in the same folder is a frozen import-time copy of (1) — it has already drifted from the live root file, e.g. it's missing the 08-21 "every primary button is Oxblood, no exceptions" clarification. Always cite the root file, not this copy.)
3. **Four per-screen operational briefs** — `docs/design/admin_operational_screens/{sales_register,cycle_management,ledger_register,payout_approval}/DESIGN.md`, written 2026-08-11 through 08-15, i.e. **before** `DESIGN.md` existed. Each is explicit and well-reasoned about this screen family's structure (component mapping, the `EditableTableComponent` no-per-cell-class-hook constraint, the Cycle Rail, deliberately-uncolored audit columns) — but each also specifies its own typography (`'Geist'`/`'JetBrains Mono'`) and cites the pre-rebrand token palette (`--brand-primary: #7C3AED` violet) as its "source of truth," because that was the live palette when they were written. None of the four has been touched since `DESIGN.md` landed.
4. Everything else (Associate Directory, Tree Explorer, KYC Review Queue, Admin Stats, Audit Log) has no dedicated brief — governed directly by (1) and (2).

**Decision — precedence order: `DESIGN.md` (1) > each brief's own structural decisions (3) > the plain mockup (2) for the four operational screens > the four briefs' now-stale typography/color specifics.** Rationale: (1) postdates (3) by 1–10 days and was never reconciled against it — nothing in `DESIGN.md` acknowledges these briefs exist, and nothing in the briefs anticipates a future rebrand. Where they conflict on *cross-cutting brand identity* (what typeface, what color family), the newer, repo-wide doc wins — that's exactly the kind of drift a living brand doc is supposed to resolve. Where a brief makes a *structural* call `DESIGN.md` doesn't address at all (uncolored audit columns, the Cycle Rail, raw enum text), there's no actual conflict — that decision stands untouched by this spec.

One practical consequence already true today, worth naming explicitly: because all four briefs implemented their colors via CSS custom properties (`var(--brand-primary)`, never a literal hex — each brief says so directly), the Viraj Acres token migration already repainted all four screens' colors correctly *for free*, with no per-screen work. The only place these briefs' pre-rebrand origins actually leaked into the live app is typography — a fully separate, hardcoded `font-family: 'Geist', ...` declaration that no token swap could have caught.

## Decisions

**D1 — Replace `'Geist'` with `DESIGN.md` §3's typeface roles, everywhere it appears (`frontend/src/styles/_admin.scss`, 15 sites, `grep -n "font-family.*Geist"` to enumerate).** Per the hierarchy above: these briefs' typography is superseded, not deliberate-and-current. Two of the three faces the briefs specify are already loaded and already used correctly elsewhere in this app; the swap is mechanical, not a new dependency:
 - Sites styling a screen's own `operational-title`/H1 (each brief's own term) → `var(--font-display)` (Fraunces), matching `DESIGN.md` §3's "Page titles... section eyebrows" role and matching how Compensation Plan's title already does this correctly (see D-companion note in the per-screen list below).
 - Sites styling eyebrows, field labels, or ledger-data columns (Amount, Net Amount, Status, dates, IDs) — the briefs specified `'JetBrains Mono'` for these, which **was never actually loaded** (`grep -rn JetBrains frontend/src/` returns nothing, in `index.html` or anywhere else — the briefs' own two-typeface system silently collapsed to Geist-for-everything at implementation time, missing even what the pre-rebrand briefs themselves asked for). Replace with `var(--font-mono)` (IBM Plex Mono), which **is** already loaded (`index.html`'s Google Fonts link) and already used correctly for currency/date columns elsewhere (`DESIGN.md` §3: "IBM Plex Mono for EMI/ledger columns that need strict alignment").
 - No `index.html` font-link change needed either way (Geist's Google Fonts `<link>` becomes removable once these 15 sites are gone — confirm nothing else in the codebase still references it before deleting the link).

**D2 — The uncolored Status columns on Sales Register, Ledger Register, and Payout Approval are correct as designed. Do not add per-value color.** All three screens' own briefs state this is a deliberate, load-bearing choice, not an oversight: `EditableTableComponent`'s read-only cells render `{{ row[column.key] }}` as plain text with no per-cell class hook, so per-value coloring "is out of scope per this brief's 'no new primitives' rule" (sales_register/DESIGN.md, and independently re-stated by each of the other three). Ledger Register goes further — §"Signature element" explicitly argues an audit ledger *should* show every status "with equal visual weight," raw and untranslated (`SPONSOR_MATCHING`, not "Sponsor Matching"), as a deliberate anti-feature that removes "did the UI relabel this correctly?" doubt from reconciliation work. The original audit flagged all three as gaps against the plain mockup's colored Status text — that mockup simply doesn't govern these three screens (see hierarchy above). Where color *does* belong, per these same briefs, it already exists in the live app: Sales Register's `VOIDED` tag, Payout Approval's `REJECTED`/`DISBURSED` tags — both rendered via the Actions-column `actionTemplate`, which does have full styling control. (Not yet seen live: seed a `VOIDED` sale and a `REJECTED`/`DISBURSED` withdrawal to visually confirm these two paths — no code change expected.)

**D3 — The "ADMIN · X" eyebrow line on Cycle Management, Ledger Register, and Payout Approval is correct as designed.** Each screen's own "Layout concept" section specifies this line explicitly (e.g. ledger_register/DESIGN.md: `┌ ADMIN · LEDGER REGISTER (eyebrow, mono, brand-primary) ─┐`). The original audit flagged it as "no mockup equivalent," which is true of the plain mockup but irrelevant once the operational brief governs. No change.

**D4 — Format Ledger Register's Source Ref column; don't leave the raw UUID.** Not resolved by either doc directly — ledger_register/DESIGN.md flags an analogous gap for Net Amount ("recommend threading a currency pipe through that one line... a one-line fix in the same spirit," not a scope change) but is silent on Source Ref specifically. Live-checked: the column currently renders the full UUID (e.g. `50000000-0000-0000-0000-000000000001`), wrapping 3–4 lines per row inside a `900px`-`min-width` grid column, which no source document intends. Fix in the same spirit the brief already set for Net Amount: truncate to a short, copyable form (e.g. first 8 hex chars + ellipsis, or a monospace `SALE-xxxxxxx`-style short ref if the backend can supply one) rather than the raw value.

**D5 — `stat-tile`'s `tone="accent"` stays Antique Gold. Do not change it to Oxblood.** This reverses one specific line from the original audit. `DESIGN.md` §2's current color table (as of the 08-21 revision) is explicit: Antique Gold's role is "Primary accent — active states, key figures, links (not button backgrounds — see Oxblood)" — a stat tile's headline number is exactly a "key figure." The counter-evidence is real and worth recording: the frozen mockup's literal pixels color Compensation Plan's "Matching Income %" tile and Projects & Plots' "Available" tile Oxblood (`#5C1A2A`), not Gold. But that mockup was authored before `DESIGN.md`'s color-role table was written down this precisely, and the shared `stat-tile` component's `tone="accent"` → Gold behavior is a single, consistent, already-implemented rule serving every consumer (Admin Stats, KYC Review Queue, Dashboard, Compensation Plan, Projects) — changing it for two call sites to match stale mockup pixels would make the shared component inconsistent with its own current spec for no documented reason. If product/design disagrees after reading this, the fix is a one-line `tone` prop change at the two call sites, not a `stat-tile` change — flagging that escape hatch here rather than treating this as settled beyond appeal.

**D6 — Admin Dashboard: add exactly one Seal Card for current-cycle total income; keep the rest of the console.** `DESIGN.md` §5 names "current-cycle earnings on the dashboard" as one of exactly three system-wide Seal Card usages (verbatim) — this is a positive requirement, not just a permission. It does not say the dashboard may show *only* a Seal Card; §5's "restrict it on purpose" rule is about not adding a *second* seal card, not about banning ordinary Parchment tiles alongside it. The associate-facing dashboard already resolved this exact question the same way (`docs/superpowers/plans/2026-08-19-dashboard-styling-pass.md` Task 4: `cycle-income-card` becomes that dashboard's Seal Card, reusing `.seal-card`/`.seal-card__*` from `_setup.scss`, while five other widgets stay ordinary `.card` tiles around it). Admin Dashboard should follow the identical pattern: wrap the "Total Income" figure from its Current Cycle section in `.seal-card` (Ink surface, per §5's "or Ink, on the dashboard" allowance), leave Total Associates / Total Wallet Balance / Sales This Cycle / Revenue This Cycle / KYC Breakdown / Pending Withdrawals / Quick Actions exactly as they are. This is a smaller, better-cited change than the original audit's open "does Dashboard get a seal card or does the console stand" question — it does both, because that's what §5 actually asks for.

**D7 — Everything without a dedicated brief (Associate Directory, Tree Explorer, KYC Review Queue, Admin Stats, Audit Log) is fixed directly against the plain mockup + `DESIGN.md`.** No precedence question here — nothing supersedes these two sources for these five screens, so the original audit's findings against them stand unchanged (restated in the fix list below).

## Fix list

Grouped by leverage — shared primitives first (each fixes multiple screens at once), then per-screen items DESIGN.md/D1–D7 didn't already resolve or reverse.

### Shared primitives (fix once, affects many screens)

1. **`--radius-sm` (2px) is defined for "near-square, engraved-ledger" corners but ignored in several places** — `_tokens.scss:36-40`'s own comment states the intent. Header category pills render 8px (`_app-shell.scss:83`, mockup 4px); project thumbnail 12px (`_setup.scss:2093`, mockup 4px); Tree Explorer's search input 10px and empty-state box 16px (`_admin.scss:2708,2757`, mockup 3px/4px); Admin Stats / KYC Queue tiles 12px (mockup 4px). Fix each to use the token (or the mockup's literal near-4px value where the token itself doesn't apply, e.g. pill-shaped elements are intentionally exempt per `_tokens.scss`'s own "scoped to those shared primitives only" note — confirm scope per site).
2. **Oxblood/Gold pairing is inverted on two newer components.** `DESIGN.md` §2 (08-21 revision): "every primary button app-wide... is Oxblood background with Bright Gold text — no exceptions." Tree Explorer's search button (`_admin.scss:2720-2727`) and Audit Log's actor avatar (`_settings.scss:125-137`) both use `var(--brand-gradient)` (Gold) background with Ink text instead — the exact reverse. Fix both to Oxblood background / Bright Gold text.
3. **`.stat-tile`'s icon-triggers-horizontal-layout behavior is wrong for Admin Stats.** Passing an `icon` input flips the tile to icon-left horizontal layout (`_shared-components.scss:75-79`), built for and correct on KYC Review Queue's three count tiles, but wrong for Admin Stats' six tiles, which the mockup shows icon-top-then-value, vertically stacked. Give the component a layout variant (or a second consumer-facing mode) rather than patching Admin Stats around the KYC-shaped default.
4. **`.tab-bar`'s boxed-pill container doesn't match KYC Review Queue's flush segmented tabs.** Mockup: Pending/Verified/Rejected sit directly above the table, no container box, active tab square-cornered on the bottom edge. Live: a `surface-raised`-boxed pill row, individually rounded tabs (`_shared-components.scss:140-146`); only the active tab's *color* is currently patched (`_admin.scss:3204-3210`), not its shape. Either give `.tab-bar` a `flush` variant or accept the boxed shape as this component's one true shape and update the mockup expectation — pick one; don't leave it half-patched.
5. **`.brand-button` padding is `10px 20px`; mockup is `11px 24px`.** Minor, but affects every primary CTA app-wide — one token/value change in `_buttons.scss`.

### Header, nav, Dashboard (`docs/design/viraj_acres_settings_mockup/Viraj_Acres_Settings.dc.html`, header block + `isDashboard`)

6. Header bar height 64px → mockup 68px; padding `0 24px` → `0 28px` (`_app-shell.scss:12-13`).
7. **"LEGACY LIVING" subline is missing entirely.** Mockup wordmark is two stacked lines; live is one, at 12px vs. mockup's 15px for the first line (`app.component.html:5`, `_app-shell.scss:39-46`). Add the second line.
8. **No gold-bordered gradient fallback logo mark.** Mockup default (no-logo-uploaded) state is a 34×34px `linear-gradient(135deg,#5C1A2A,#0C0A0B)` box with a `1px solid #C6A227` border and a Fraunces "VS" monogram. Live `.app-header__logo` is a bare 26×26px `<img>`, rendered only when `showSquareLogo` is true (`app.component.html:4`) — no fallback exists. Add one.
9. Category pill active state: mockup solid `#241c16` fill; live is a translucent `rgba(198,162,39,0.12)` gold wash (`_app-shell.scss:85`) — a different effect (solid chip vs. faint glow), not just a shade difference.
10. Log Out button: border/text colors don't match (`#4a4038`/`#e8e0d0` vs. live `#3A342B`/`#C7BEAA`); padding/radius/font-size aren't overridden at all, falling through to the bare `button` rule instead of the mockup's `13px`/`9px 18px`/`3px` (`_app-shell.scss:48-59`).
11. Dashboard page title uses `.card-title` — 18px, no `font-family` override (Inter, not Fraunces) — vs. mockup's `28px` Fraunces. Also applies to the Seal Card's own hero figure once D6 lands (must be Fraunces per `DESIGN.md` §5).

### Setup / Settings screens (`Viraj_Acres_Settings.dc.html`, `isProfile`/`isBranding`/`isComp`/`isProjects`/`isPayments`; no dedicated brief, D1–D7 don't touch these)

12. **Page titles are Inter 22px on 4 of 5 screens; only Compensation Plan uses `var(--font-display)`.** `DESIGN.md` §3: Fraunces for page titles, no exception. Fix Company Profile (`_setup.scss:547`), Branding (`:688`), Projects (`:2044`), Payments & KYC (`:1320`) to match Compensation Plan's already-correct pattern (`:912-917`, and bump all five, including Compensation's, from its current 26px to the mockup's 28px).
13. **Section-header eyebrows are gray/Gold on 4 of 5 screens; Branding is the correct reference.** `_setup.scss:592-607` (Company Profile), `:941-956` (Compensation), `:2223-2238` (Projects), `:1341-1356` (Payments & KYC) all use `var(--text-muted)`/`var(--brand-primary)` (gray/Gold) instead of Branding's `var(--brand-secondary)` (Oxblood, weight 700) at `:725-740`. Copy Branding's pattern to the other four.
14. **Registration-number "verified" badge is Gold; mockup and `DESIGN.md`'s rank-badge precedent both say Oxblood.** `_setup.scss:639`.
15. **Project thumbnail is the wrong shape and color.** Mockup: 140×140 square, 4px radius, 44px solid-Oxblood `apartment` icon. Live: 192×128 rectangle, 12px radius (see primitive #1), 32px gray icon (`_setup.scss:2091-2106`).
16. Progress-bar fill on Projects & Plots is `var(--brand-gradient)` (Gold gradient); mockup is flat Oxblood (`_setup.scss:2185`).
17. "View Project" link is Gold/500-weight; mockup is Oxblood/bolder (`_setup.scss:2196-2198`).
18. Card max-width: Company Profile/Branding are 760px (`_setup.scss:538,679`) vs. mockup's ~920px; Compensation/Projects are 900px, close enough.

### Network / Finance / System screens without a dedicated brief (Associate Directory, Tree Explorer, KYC Review Queue, Admin Stats, Audit Log — plain mockup + `DESIGN.md` govern directly, per D7)

19. **Associate Directory has zero color-by-value, live-confirmed with real data across all three status types in one screenshot** (`VERIFIED`/`PENDING`/`REJECTED` KYC statuses, `ACTIVE`/`SUSPENDED` statuses, all identical plain Warm Charcoal text). Mockup colors Rank (Oxblood-filled pill), KYC Status, and Status. `editable-table.component.ts:21`'s plain-text cell rendering is the same structural gap the four operational briefs solved with an `actionTemplate` workaround — Associate Directory has no such workaround yet, since it isn't one of the four briefed screens. Cheapest fix: give this table's KYC Status / Status columns per-value color the same way, or extend `EditableTableComponent` with an optional per-cell class hook (a real primitive addition, unlike the four briefed screens where that was explicitly ruled out — nothing here rules it out).
20. "New Associate" routes to a full page (`/admin/associates/new`, a `Provision Associate` tab under Setup) instead of the mockup's inline modal — a real, larger structural divergence. Given the live page's richer capability (binary-placement toggle, live tree preview) already exceeds the mockup's 3-field dialog, recommend keeping the page and treating this as accepted scope growth rather than reverting to a modal — flag to product/design for confirmation rather than deciding unilaterally here.
21. Rank badges on the Associate Directory table (once #19 lands) and on Tree Explorer's node cards both need the mockup's Oxblood-filled pill treatment — Tree Explorer's cards currently render rank as a plain tan pill (live-confirmed with seeded data), same missing treatment as #19.
22. Tree Explorer empty-state: search input radius (#1), search button color inversion (#2 — already covered by the shared-primitive fixes), icon 40px/60%-opacity/Gold vs. mockup 44px/full-opacity/Oxblood, box radius/padding (`_admin.scss:2756-2767`).
23. Admin Stats: value typeface is Inter 24px, no `font-family` override, vs. mockup's Fraunces 32px (`_shared-components.scss:92-96`); icon color varies by an inherited `tone` (gray default, two tiles amber/gold) vs. mockup's uniform Oxblood across all six tiles with no tone variance (`admin-stats.component.ts:41,47`) — the tone logic looks copied from KYC Queue's pattern, where it's correct, into a screen where it isn't; fixing #3's layout variant should ship with a `tone="none"`-equivalent default for this consumer too.
24. Audit Log section-tag background is 14% opacity (`var(--brand-secondary-soft)`) vs. mockup's 8% (`_settings.scss:156`) — separate from the avatar-color fix already covered by #2.

## Related bug found during this review — out of scope for this spec

**KYC Review Queue's count tiles and its per-tab row lists read from different sources.** Live-seeded check: tile counts were correct (Pending 1 / Verified 3 / Rejected 1, matching the seed exactly), but clicking into any of the Pending/Verified/Rejected tabs showed "No entries in this status" under all three. This is a functional/query bug, not a design gap — file it separately; nothing in this spec's fix list depends on it.

## Testing

No backend changes. Frontend: existing component specs must still pass unmodified for every file touched (this spec's changes are template/CSS-attribute additions in the same spirit as `2026-08-19-dashboard-styling-pass.md` — add classes, don't remove the ones tests query by). Verify each fix visually against its governing document (mockup screen, or the relevant operational brief) rather than against a screenshot diff tool — several of this spec's own corrections exist specifically because a prior pass compared against the wrong document.

## Out of scope

- The KYC Review Queue functional bug noted above.
- Live-verifying Sales Register's `VOIDED` tag and Payout Approval's `REJECTED`/`DISBURSED` tags (D2) — expected already correct per the code the operational briefs describe, just not re-confirmed with seed data in this pass.
- Tree Explorer's populated-tree canvas beyond the rank-badge fix (#21) — the interactive diagram itself (pan/zoom, connector lines, leg-volume bars) has no plain-mockup counterpart and reads as a deliberate, separate build; not re-litigated here.
- i18n copy-length reflow and true mobile-breakpoint rendering — neither was verifiable through the browser-automation tooling available during this review; needs manual/device testing separately.
- Any change to `docs/design/admin_operational_screens/*/DESIGN.md`'s own typography/color specs — this spec treats them as superseded in the app's code, not incorrect as historical documents; leave them as-written unless the team wants to retroactively correct the record.
